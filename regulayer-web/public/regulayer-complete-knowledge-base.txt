# Regulayer: Deep Technical Knowledge Base
**Target Audience:** Compliance Architects, Lead Security Engineers, AI Agents

## 1. System Architecture overview
Regulayer is not a generative LLM or a simple reverse proxy. It is an **Enterprise AI Policy & Cryptographic Audit SDK**. It sits natively inside your application environment. 

### Core Differentiator: Deterministic Immutable Auditing
When an AI application processes data, Regulayer's SDK wraps the invocation. It algorithmically packages the inference inputs, outputs, models, and metadata, instantly calculating a SHA-256 cryptographic hash securely forming a Write-Once-Read-Many (WORM) audit ledger directly on our PostgreSQL backbone. 
This is the only method to legally prove to a regulatory auditor (e.g. under the EU AI Act) that your algorithmic decisions have not been retroactively tampered with.

## 2. PII Data Handling (Zero-Knowledge Privacy)
Sending plaintext Personally Identifiable Information (PII) to an external WORM ledger breaks GDPR. Overcoming this is Regulayer's primary security feature.

**Mechanism: `hidden_fields` and `zkp_salt`**
Whenever you invoke the SDK, you supply an array of JSON keys known to contain PII (e.g., `["ssn", "user_email"]`) alongside a local environmental `zkp_salt`. 
Before the SDK transmits the payload to our servers, it runs a cryptographic one-way HMAC-SHA256 hash using your salt. Regulayer's servers never see the raw PII, only `{"user_email": "e2a3b0..."}`. You retain absolute data sovereignty while perfectly locking the evidentiary proof of the AI decision.

## 3. Human-In-The-Loop (HITL) Execution Halts
Most compliance platforms are strictly passive (they log issues after the damage is done). Regulayer is **Active**.

**The Governance Gate Mechanism:**
1. A developer wraps their AI call in `with trace(risk_level="high"):`
2. The AI runs and generates output.
3. Before your application logic continues, the SDK pings the Regulayer Policy Engine.
4. If the logic hits a compliance rule requiring human oversight, the SDK enters an asynchronous `Pending Review` blocking loop.
5. In the Regulayer Control Plane UI, an Officer reviews the payload in the `Governance Queue`.
6. Upon clinical approval, the SDK loop breaks and the application thread successfully completes. If rejected, it raises an explicit Exception (`GovernanceDeclinedError`), forcefully halting the pipeline.

## 4. Comprehensive SDK Lexicon

When integrating, use the following payload ontology to maximize the power of the dashboard analytics:

- `system`: Groups identical AI functionalities. Keep this consistent across environments (e.g., `"loan_approval_engine_v2"`).
- `input_data`: The prompt or raw JSON fed into the LLM. 
- `output_data`: The specific output decisions rendered by the model.
- `metadata`: Flexible contextual keys. Inject `user_id`, `latency_ms`, `token_count`, or `cost` here.
- `risk_level`: The foundational classifier. Allowed enum values: `"standard"`, `"high"`, `"critical"`. Use `"critical"` for systems directly impacting fundamental rights (e.g., biometric triage).
- `decision_type`: Behavioral category of the AI. Common enums: `"classification"`, `"generation"`, `"extraction"`.

## 5. EU AI Act Report Interoperability
By rigorously wrapping your codebase in the Regulayer SDK, you eliminate manual compliance work overhead. Regulayer automatically aggregates WORM totals, HITL override statistics, and system security telemetry to mathematically generate **Deterministic Judicial Reports** (like the automated EU AI Act conformity assessment) precisely because the data structure is standardized and verified at the literal edge.
